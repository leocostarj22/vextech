# Vextech — guia do projeto

Site experimental da Vextech, baseado na demo Margem. O utilizador aprovou testar a direção visual 01 antes de decidir se a mantém. A referência está em docs/proposta-visual-01.md.

- Vite, JavaScript, Three.js, GSAP e Lenis, sem framework.
- Conteúdo em português de Portugal. Três serviços: consultoria especializada, projetos chave-na-mão e nearshore. Não inventar métricas, clientes, equipa ou testemunhos.
- Vagas em Carreiras vêm da API própria em server/ (Node/Express + MySQL/MariaDB), não de texto fixo no site; o admin insere-as pelo painel em /admin, não editando código. As duas vagas atuais (Java Developer no Porto, PHP Developer em Braga) foram copiadas do site real vextech.pt — só os campos lá publicados (título, localização, requisitos); nunca inventar contrato, descrição ou benefícios que não estejam na fonte. Em desenvolvimento, o frontend pede `/api/vagas` ao Vite, que encaminha para `http://127.0.0.1:3001` sem exigir `.env` nem CORS; `API_PROXY_TARGET` permite alterar o destino. Sem API disponível ou sem vagas publicadas, manter candidatura espontânea, mensagem explícita e acesso à página de vagas. Em produção corre na VPS em https://leocostadeveloper.com/vextech/ (cPanel/AlmaLinux, MariaDB, processo pm2 `vextech-api` na porta 4001 atrás de um proxy Apache). Ver README.md, secção "Vagas e painel de administração".
- Deploy em subcaminho: o build de produção usa `PUBLIC_BASE_PATH=/vextech/ npm run build` (sem a variável, o build local serve a partir de "/", sem alterações); por isso qualquer caminho absoluto novo no código usa sempre `import.meta.env.BASE_URL`, nunca `/` fixo. `public/.htaccess` (versionado, copiado para `dist/` em cada build) reencaminha `/vextech/api`, `/vextech/admin` e `/vextech/uploads/vagas` para o Node local; o painel de admin resolve os seus próprios pedidos `fetch` a partir do caminho da página atual (`new URL("../api/...", location.href)`), nunca `/api/...` absoluto, para funcionar sob qualquer prefixo. `server/ecosystem.config.cjs` descreve o processo pm2; `.github/workflows/deploy.yml` builda e publica no push para main, mas só corre depois de configurados os segredos `VPS_HOST`/`VPS_USER`/`VPS_SSH_KEY` no GitHub — até lá, atualizar manualmente por SSH (`git pull`, rebuild, `pm2 restart ecosystem.config.cjs`).
- MariaDB (produção) trata o tipo `JSON` como `LONGTEXT` e o `mysql2` não o descodifica automaticamente como faz no MySQL; as rotas `GET` de vagas em `server/src/routes/vagas.js` aplicam `JSON.parse` defensivo ao campo `requisitos` antes de responder. Qualquer nova coluna JSON precisa do mesmo cuidado.
- Cores em src/styles/tokens.css: #11111f, #68d2df e branco. O tema inicial respeita `?tema=`, depois a escolha guardada e depois o sistema (`prefers-color-scheme`). As superfícies, o fundo e o nevoeiro Three.js acompanham a escolha.
- Logótipos originais em SVG em src/brand/vextech-*.svg, convertidos dos vetores PDF enviados pelo utilizador. Nunca redesenhar o wordmark com uma fonte.
- Tipografia editorial, linhas finas, espaço generoso, sem grelhas de cartões ou decoração neon.
- Exceção aprovada para Carreiras: cards com imagens ilustrativas, cores da marca e movimento ligado ao scroll. Na home, apenas as duas vagas ativas mais recentes; todas as vagas e requisitos completos em `/pt/vagas/`. Não adicionar vagas de demonstração como fallback. Respeitar movimento reduzido e manter candidatura espontânea quando a API não estiver disponível.
- Capas de vagas: os originais de `vagas.zip` estão em `public/media/vagas/`. A capa enviada pelo admin tem prioridade; sem envio, PHP/Java usam as imagens correspondentes (JavaScript não é Java), restantes vagas usam `default.jpg`. O backend aceita multipart PNG/JPG até 5 MB, valida e normaliza a imagem, e guarda os ficheiros em `server/uploads/vagas` (ou `UPLOADS_DIR`), fora do Git. A migração `002_capa_vagas.sql` acrescenta a coluna opcional `capa`; executar `cd server && npm ci && npm run migrate` antes de iniciar a API atualizada. O Vite encaminha também `/uploads/vagas`.
- Túnel leve: texturas partilhadas, renderização quando necessário, pixel ratio máximo 2. Mobile com texto dos destaques abaixo da imagem. Respeitar prefers-reduced-motion.
- Imagens em public/media são ilustrativas, recebidas no pacote da marca; não representam projetos de clientes nem equipa real. Ver docs/media.md.
- O contacto geral e a candidatura espontânea continuam em demonstração; não simular envio. As candidaturas a vagas específicas são reais: `/pt/vagas/detalhe/?id=ID` carrega a descrição e todos os requisitos, e envia o formulário para `/api/vagas/:id/candidaturas`. O candidato anexa apenas PDF válido (até 5 MB) e confirma a Política de Privacidade. Currículos em `server/private/curriculos` (ou `CURRICULOS_DIR`), nunca em diretório público. Administradores consultam e descarregam via `/api/candidaturas`, com sessão, e podem eliminar a candidatura e o ficheiro. Sem envio de emails. A migração `003_candidaturas.sql` acrescenta descrição opcional e candidaturas, preservando vagas. Os cards abrem a página individual; não abrem o formulário de demonstração.
- Validar com npm run build e npm test. Conferir desktop 1440×840 e mobile 390×844.
- Cada tarefa já decorre num ambiente isolado. Usar o checkout existente, sem criar Git worktrees salvo pedido explícito.

A demo Margem está preservada na tag margem-demo-v1, commit 77ba3a4c178cbc8180e0d10be9b42e3f3348d862. Não fazer reset destrutivo para regressar: consultar README.md e preservar trabalho local.

- Tema escuro atual: degradê de azuis com base #10111e. O canvas transparente deixa passar o fundo CSS; as fotos desvanecem com a distância por opacidade para evitar retângulos de cor sólida sobre o degradê.
- Abertura das páginas públicas: `build/abertura.js` injeta CSS crítico, `src/abertura/boot.js` e os SVG originais no HTML. A máscara azul atravessa a marca ao centro; o tema é escolhido antes dos módulos. A home espera pelas texturas iniciais e fontes, sem esperar pela API de vagas; as outras páginas sinalizam prontidão após renderizar. Limite de segurança de 6 segundos, movimento reduzido sem varrimento nem demora mínima e páginas legais legíveis sem JavaScript. O wrapper `#conteudo-site` fica temporariamente inert. Não remover o salto acessível: o CSS crítico esconde-o até receber foco pelo teclado. Ver `docs/abertura.md`.

- Centro de talento aprovado: fase 1 implementada em `server/public/admin/`, com dashboard real, temas, candidaturas paginadas/pesquisáveis e ficha lateral com PDF autenticado; vagas e convites preservados. Resumo em `/api/recrutamento/resumo`; o painel usa `/api/candidaturas?pagina=...`, mantendo a listagem antiga sem parâmetro por compatibilidade. Migração `004_recrutamento_indices.sql` só cria índices. MySQL em UTC, dias/horas apresentados em Europe/Lisbon; não reescrever datas históricas automaticamente. Ver `docs/recrutamento/implementacao-fase-1.md`. Funil/etapas, notas, responsáveis e agenda ficam para fases seguintes; não alimentar a interface real com exemplos do protótipo. Recursos da marca e Geist acompanham o backend em `server/public/admin/assets`. Proxies Vite incluem `/admin`, `/api/auth` e `/api/recrutamento`.

- Perfil do administrador em `/admin/index.html#perfil`: nome, email e password próprios; `GET/PUT /api/auth/perfil` e `PUT /api/auth/password`, sempre com sessão e confirmação da password atual. Nova password confirmada, mínimo 8 caracteres e máximo bcrypt de 72 bytes UTF-8; nunca guardar passwords no browser ou devolver hashes. Migração `005_perfil_admin.sql` acrescenta `utilizadores.versao_sessao`; email/password incrementam-na e renovam apenas a sessão atual. O middleware verifica a conta e a versão na BD em todos os acessos privados, incluindo PDFs. Tokens anteriores sem versão equivalem a zero. Testes autenticados devem criar uma conta real na base dedicada, em vez de assumir ID 1.

- Password esquecida: `cd server && npm run reset:admin` usa o MySQL de `server/.env`, pede email e password/confirmação ocultas num terminal interativo e incrementa `versao_sessao`. Não passar passwords por argumentos, não imprimir hashes, não abrir um reset público sem autenticação. A implementação partilha a validação de password com o perfil e mantém o ID, nome/email e os dados de recrutamento.
